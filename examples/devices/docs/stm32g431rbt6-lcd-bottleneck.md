# STM32G431 `HAL_06_LCD` 稳态清屏瓶颈

诊断基准：`ce68fbd`，2026-11-19。器件架构和此前的完整基准记录见
[STM32G431RBT6 器件文档](stm32g431rbt6.md)。

## 结论

30 ms 的稳定清屏窗口实测耗时 **120.16 ms**，约为实时预算的 **4.0 倍**。剩余成本主要来自
**逐边沿同步发布及其两侧的生成代码**，不是翻译、宿主 direct 派发或某一个求解函数。
两轮 CPU 采样中，发布与续跑检查点合计占 48.3–54.7%，不含检查点的生成代码占 29.7–37.6%。
只换状态镜像的存储方式实测快了 4.1%；只优化其中一个热点不足以填平差距。

## 测量口径

- 真实 `HAL_06_LCD.bin`，固件自行配置 80 MHz，`throughput`，裸 MCU 只接 VDD/VSS；
  GPIO 仍正常发布。固件在 `test/ili9325/fixtures/` 下，SHA-256 为
  `673d0b78c9376e0bae99761b6285cc2d2e00b3d44c6eefb7cf040a2992945650`。
- 只比较仿真时间 360–390 ms。初始化、进入绘图、清屏结束和等待不计入稳态收益。每个
  独立进程运行三轮，取后两轮作暖轮；A/B 只比较同一固件、板型和工作量的无探针墙钟。
- 宿主为 Intel Core i7-12700K，Node.js v24.20.0。计数、CPU 采样、V8 跟踪和逐边沿
  签名分别运行，不用其墙钟衡量提速，也不以 CT117E-M4 历史数据作基线。

## 已提交优化

| 对照                  | 改动                                                |       稳定窗无探针暖轮中位数 |
| --------------------- | --------------------------------------------------- | ---------------------------: |
| `77d1a45` → `115d42b` | 发布后直接续跑；宿主 direct 调用由 208,799 降至 126 | 287.13 → 162.35 ms（−43.5%） |
| `115d42b` → `08f137c` | 已准入的单槽叶计划直接按板序提交                    | 161.98 → 122.82 ms（−24.2%） |
| `08f137c` → `ce68fbd` | 空后缀复用调度准入，仍结算原后缀边界                |  126.11 → 120.16 ms（−4.7%） |

各行是独立 A/B，不应把不同行的绝对墙钟串成一次测量。最后一组正反序对照分别是
125.66 → 118.02 ms 和 128.13 → 124.36 ms；合并后每种版本各四个暖轮。
`ce68fbd` 稳定窗有 104,338 次 WR 采样变化和 126 次宿主 direct 调用，无新翻译、
direct 编译或回退。

## 剩余成本在哪里

`ce68fbd` 的单独计数运行在同一窗口观测到：

| 工作                                               |              次数 |
| -------------------------------------------------- | ----------------: |
| 单槽电气发布及样本提交（PB5 104,338；PB9 104,337） |           208,675 |
| 带电气更新的边界 / 无电气更新的边界                | 208,675 / 208,797 |
| 准入的前缀发布与空后缀续跑对                       |           208,673 |
| 标量状态槽提交及版本递增                           |         1,252,831 |

每次单槽更新前还有一次 VDD1 样本读取和一次缓存电阻意图查询。裸板边界未观察到待处理的
观察者，故这部分成本在 LCD 渲染或联合板反应开始之前就已经存在。按整个窗口摊销，
120.16 ms 相当于每次电气发布 **576 ns**（包含生成代码和窗口内其他工作）；实时预算只有
**144 ns**，总墙钟需要再降约 **75%**。

两轮 CPU profile 只统计计时范围内的样本，以下按调用栈互斥归类：

| 调用栈分类                 |   采样占比 |
| -------------------------- | ---------: |
| `frame.publishCheckpoint`  | 40.4–47.7% |
| `frame.finishCheckpoint`   |   7.0–7.9% |
| 生成 shard，不含上述检查点 | 29.7–37.6% |
| 其他（含可能的内联归属）   | 14.1–15.6% |

按函数自身归因，`commitDirectStates` 占 12.4–14.2%，`flushDirect` 占 5.1–5.2%，
`solveSlots` 与 `applySingleLeaf` 合计约 14.4–14.5%，`canContinueDirect` 仅 0.4–1.6%。
生成代码的样本分散在指令前缀、GPIO 意图、后继与退出、脏字与守卫、时间推进与检查点入口，
没有单一支配点。若按采样占比从墙钟扣除整个检查点栈，仍剩约 **54–62 ms**；这是量级估算，
不是实测反事实，也不是可以相加的提速预测。

### 已验证的局部假设

- **状态镜像确实可压缩，但收益有限。** 临时原型把热提交中的 `Map.set` 换成预绑定的
  已提交数组槽，保留暂存银行、脏位扫描、提交顺序及版本递增。正反序无探针 A/B 的暖轮中位数
  分别为 **123.26 → 113.19 ms** 和 **115.10 → 112.43 ms**；
  合并为 **117.98 → 113.19 ms（−4.1%）**，仍约为实时预算的 3.8 倍。
  裸板 WR 和联合板签名均用非空文件 `cmp` 一致，
  独立 LCD 总线 oracle 通过。原型未提交，也未作为全外设门槛的验收版本。
- **V8 没有因字节码过大而拒绝这四个热 shard。** 在 Vitest worker 中单独跟踪，
  `115/117/118/119` 的字节码分别为 28,749 / 25,676 / 26,892 / 27,149 字节，均低于
  61,440 字节上限，并在稳态窗进入 TurboFan。前两轮的 `118/119` 各退优化一次后重新优化；
  最后一轮这四个 shard 未见退优化。这不排除生成代码布局和内联质量仍可改进。
- **共享 shard 派发尾部、合并空后缀交接**均未证实有稳定的额外收益，未保留。

## 基线等价验收

`ce68fbd` 与 `08f137c` 的裸板 WR 时间线、联合板全引脚时间线、GRAM、帧及合成负载 220 窗
输出签名分别写入非空文件后直接 `cmp` 一致。440 ms 独立 LCD 总线 oracle 核对了
157,338 个 WR 边沿、77,351 次 GRAM 写入和 3 帧；联合板记录 648,733 条全引脚样本。
合成负载保留 4 ms 仿真预热和 220 个 2 ms 窗；末 40 窗 **40/40 达到实时**，墙钟中位数
**1.091 ms**，通过 ≤2 ms 门槛。

## 优化复测（尚未达到实时）

预绑定 GPIO 样本与意图、延迟状态镜像、复用电气叶计划，并按翻译结果布置直接后端的后继
路径后，裸板 360–390 ms 清屏窗口的暖轮中位数为 **71.93 ms**，保留版本复测为
**71.32 ms（0.42× 实时）**，复测三轮墙钟分别为 **77.33 / 75.50 / 67.13 ms**。
相比历史基线 120.16 ms 耗时少约 41%，仍高于 30 ms 预算。未做同机交错 A/B，不能据此
分离各项改动的收益。

三轮均记录到 **104,338 次 WR 采样变化、126 次 direct 调用**，窗口内无新翻译、编译或回退。
71.93 ms 对应版本的 440 ms 联合 LCD oracle 通过；覆盖 **648,733 条全引脚样本**的时间线、
GRAM 和帧签名与保存的基线文件 `cmp` 一致。保留版本通过了独立的完整外设实时验收：
末 40 个 2 ms 窗全部达标，墙钟中位数 **0.871 ms**。该负载不计入 LCD 清屏成绩。

优化后两轮 CPU 采样中，生成代码（不含检查点）约占 **45%**，发布与续跑检查点合计占
**41–51%**；单个热 shard 约占 **40%**。这些是采样归因，不是可直接扣除的墙钟。

进一步把较长的单臂分支移出热 shard，暖轮中位数为 **76.75 ms**，未见收益，未保留该策略。

## 单槽叶计划准入缓存实验

候选为单脏槽提供独立求解入口。通过拓扑守卫后，同一槽可以按意图对象身份重放已准入叶计划；
进入通用求解会使缓存失效。批量叶重放只把现有边移到另一固定参考，不改变未知节点的度数。

对照 `6304576`，在同机同 CPU 集合上用 Node.js v24.20.0 交错运行无探针裸板基准。每个
进程剔除第一轮，表中为后两轮墙钟及其中位数（ms）：

| 顺序        | 对照暖轮      | 对照中位数 | 候选暖轮      | 候选中位数 |
| ----------- | ------------- | ---------- | ------------- | ---------- |
| 对照 → 候选 | 78.11 / 69.15 | 73.63      | 79.72 / 66.16 | 72.94      |
| 候选 → 对照 | 75.96 / 67.92 | 71.94      | 74.78 / 60.43 | 67.61      |

合并各版本的四个暖轮，中位数从 **72.55 降到 70.47 ms（−2.9%）**。每轮仍有 104,338 次
WR 采样变化、126 次 direct 调用，无新翻译、编译或回退。两组中位数方向一致，但单轮有反转；
追加复测前不把 2.9% 视为稳定收益。原始日志位于 `/tmp/opencode/g431-leaf-admission.Ocw4q8/`。

裸板 WR 时间线与基线签名 `cmp` 一致；440 ms 联合 LCD oracle 通过，648,733 条引脚样本的
时间线、GRAM 和帧签名也 `cmp` 一致。独立的完整外设实时验收末 40 个 2 ms 窗全部达标，
墙钟中位数 0.855 ms。21 项叶传播测试、19 项 JIT 回归、真实 adapter 的 423 项符合性用例及
100 个生成 oracle 用例均通过。

## 下一步

先为翻译后控制流中的短热路径生成带守卫的直线代码，在边界之间复用寄存器值和静态后继；
不硬编码固件 PC。每个 GPIO/WR 边沿、时间戳和原有边界均保留；配置、拓扑、观察者、
程序或调度条件变化时回到原路径。捕获先于 TIM 推进，MMIO 同步、时钟切换及截止点语义不变。

先在同机做无探针交错 A/B，确认稳态窗有净收益，再比对裸板 WR 与联合板时间线、GRAM 和帧
签名。以 208,675 次发布的诊断计数摊销，71.32 ms 约为 **342 ns/次**（含窗口内所有工作），
30 ms 预算约为 **144 ns/次**；这不是单个发布函数的耗时。
