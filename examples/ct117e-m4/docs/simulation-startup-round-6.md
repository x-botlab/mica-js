# CT117E-M4 冷启动优化：第六轮候选

候选共享动态系统区访存处理体。对比 `34c09f3`，生产 Chromium 的 LCD 首蓝缩短 **2.135 s（25.8%）**；Node 清屏对照未满足稳态无退化要求，暂不采用为新基线。

## 改动与首步工作量

动态系统区地址判断留在访存点，命中后按读写和 1/2/4 字节调用六个共享函数。函数复用原有 NVIC、SCB 和 SysTick 逻辑；静态系统区及 SRAM、Flash、CCM、GPIO 和非 GPIO 外设路径不变。

共享函数在适配器本地构建并由宿主绑定校验；相同基础模型及 Machine 时钟配置复用函数表和绑定。直接 JIT 同步读写调用者的同一执行帧，沿用 dirty bits，并将函数读写集合纳入调用者的入口检查。不支持的调用使整条 JIT 指令在执行前回退，不在访存中间暂停、发布或重放。

独立 Chromium 首步探针（不纳入 A/B 计时）记录到两版均翻译 247 个块。块内 IR 从 **664,271 降至 456,806**；计入六个共享函数的 8,476 条 IR，合计 **465,282 条（−30.0%）**。157 个动态系统区调用点全部保留。探针结束时，直接程序覆盖 241/247 个已翻译块，含共享调用的块覆盖 75/77；快照未区分暂未纳入程序的块与直接编译拒绝的块。

## 生产 Chromium A/B

i7-12700K / Chromium 153，各三轮、新浏览器进程、无阶段探针。使用原始 `HAL_06_LCD.hex` 和固定 16 ms 步长。从点击「运行」开始计时，首蓝和十色带均按实际 LCD 像素判定；六轮均无运行诊断。

| 计时终点     |    `34c09f3` 中位数（范围） |       候选中位数（范围） |
| ------------ | --------------------------: | -----------------------: |
| 进入运行态   |    7.786 s（7.772–8.036 s） | 5.646 s（5.578–6.414 s） |
| LCD 首次蓝底 |    8.284 s（8.254–8.557 s） | 6.149 s（6.045–6.964 s） |
| 完整十色带   | 11.304 s（11.234–11.507 s） | 9.132 s（8.912–9.813 s） |

重建：`pnpm --filter @mica-js/playground build:workbench`。

## 稳态验收未过

Node.js 24.20.0、CPU 亲和性 `8,10,12,14`，按基线、候选、候选、基线各跑一组六轮，使用 `MICA_CT117E_M4_PACKAGE` 指定保存的发布器件包。每轮清屏均为 **104,338 次 WR 变化、52,169 次 GRAM 写入、2 帧**；至 440 ms 的总工作量一致。

| 360–390 ms 清屏                   |     基线 |      候选 |
| --------------------------------- | -------: | --------: |
| 两组合并，去首轮的墙钟中位数      | 29.20 ms |  39.11 ms |
| 两组合并，去首轮的进程 CPU 中位数 | 35.82 ms | 100.74 ms |
| 合并各组末两轮的墙钟中位数        | 28.64 ms |  35.29 ms |
| 合并各组末两轮的进程 CPU 中位数   | 28.61 ms |  66.02 ms |

候选修复了相同块无法跨实例复用绑定校验的问题，Node 暖轮到 10 ms 的建板加首步耗时随之恢复启动收益，但清屏中位数仍偏高。较快候选窗口仍能到约 29 ms，部分暖轮又回到 39–71 ms。

独立入口探针中，两版在清屏窗口内均覆盖 314 个 PC，逐轮均有 242 次直接尝试、62 次回退和 90 次直接截止，程序身份不变且没有新增构建。到清屏入口时，累计直接程序构建次数均为 27，当前程序的驻留分片数从 126 降为 120。另开 V8 采样的一组中，两版慢轮入口前 10 ms 都未采到 TurboFan 分片叶子，快轮则都有。采样组未重现无探针 ABBA 的差距，尚不足以归因。

板级回归覆盖 `STMIA` / `LDMIA` 顺序和写回、窄读取的 SysTick `COUNTFLAG` 读清、NVIC 优先级宽度掩码，并核对六种调用均能纳入直接程序。运行时回归另覆盖同帧内连续调用、状态和内存可见性、被观察的写入在入口回退。

## 分片布局重放

沿用 Node 清屏基准的原始固件与 10 ms 步长。独立记录第五轮和第六轮每次直接程序构建的分片 ID、分片顺序和 `case` PC 顺序，再用第六轮的共享处理体重放第五轮布局。重放只在基准加载模块时注入，不改生产源码。计时对照的两侧均走同一套重放代码：A 用第六轮自身布局，B 用第五轮布局；均不启用 V8 采样或窗口探针。

- 每轮至 440 ms 共构建 29 次直接程序。三种配置逐次的 PC 集合和续跑 ID 相同；第六轮自身与第五轮有 18 次布局不同，重放逐次恢复了第五轮的分片 ID 和有序分组。
- 清屏入口的 314 个 PC 中，81 个的同片 PC 集合改变。此前采样的三个主要热分片中，`119 → 113` 移出了 `0x08001036`，它在候选中与 `0x0800103c` 同片；`121 → 115`、`122 → 116` 的有序 PC 分组不变。后两片的生成源码除分片编号和常量池下标外相同。
- 清屏窗口的直接尝试、回退和截止次数不变，窗口内都不重建。每轮仍为 104,338 次 WR 变化、52,169 次 GRAM 写入、2 帧；至 440 ms 的总工作量、三帧的交付时刻及字节 SHA-256 也一致。

各六轮的初测（去掉首轮）中，A、B 的墙钟中位数为 **39.37 → 28.51 ms**，进程 CPU 中位数为 **101.07 → 35.78 ms**。差异主要来自 A 的第六轮再次变慢（70.54 ms）；两侧第 2、3 轮都慢，第 4、5 轮都在 30 ms 以内。因此另跑 ABBA 复核初测信号，而不把这一轮差异直接归因于布局。

ABBA 各组六轮，与前面的生产包对照使用同一 Node 版本和 CPU 亲和性。时间单位为 ms：

| 360–390 ms 清屏                   | A：候选布局 | B：第五轮布局 |
| --------------------------------- | ----------: | ------------: |
| 两组合并，去首轮的墙钟中位数      |       42.48 |         40.35 |
| 两组合并，去首轮的进程 CPU 中位数 |      105.05 |        102.89 |
| 合并各组末两轮的墙钟中位数        |       54.81 |         33.38 |
| 合并各组末两轮的进程 CPU 中位数   |      129.34 |         64.77 |
| 暖轮超过 45 ms                    |        5/10 |          3/10 |

正序组末两轮，A 为 28.33 / 70.92 ms，B 为 27.56 / 27.63 ms；反序则两侧都慢，A 为 71.63 / 38.70 ms，B 为 72.25 / 39.13 ms。**恢复布局没有稳定恢复清屏性能**：末两轮合并值改善，但正序看到的收益未在反序复现，不能把原退化单独归因于分片布局。

另跑一对 V8 采样组。两侧第 2、3 轮清屏的前 10 ms 均未采到 TurboFan 分片叶子，首次记录到新的 `stepShard` TurboFan 代码分别在 A 的 **25.32 / 15.07 ms**、B 的 **18.36 / 16.87 ms**。两侧第 4–6 轮的前 10 ms 都已有分片在 TurboFan 执行，且未复现无采样组最后两轮再次变慢的现象。采样能区分快慢轮，但还不能说明是什么触发了后期暖轮重新变慢。

诊断脚本、布局记录和原始日志保存在 `/tmp/opencode/ct117-shard-replay`。不保留生产重放补丁，也不扩大到非 GPIO 外设。下一步应在相同布局下对照快轮和后期慢轮的清屏入口，区分热点代码尚未升层与此前已升层、在进入窗口前掉层。
