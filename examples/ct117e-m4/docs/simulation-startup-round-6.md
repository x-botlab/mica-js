# CT117E-M4 冷启动优化：第六轮候选

本轮共享动态系统区访存处理体。原候选首蓝更快但清屏退化；加入[有界工厂缓存](#有界工厂缓存试验)后，生产 Chromium 的 LCD 首蓝由 **8.986 s 降到 6.516 s（−27.5%）**，Node 清屏墙钟和进程 CPU 均通过稳态验收。

## 改动与首步工作量

动态系统区地址判断留在访存点，命中后按读写和 1/2/4 字节调用六个共享函数。函数复用原有 NVIC、SCB 和 SysTick 逻辑；静态系统区及 SRAM、Flash、CCM、GPIO 和非 GPIO 外设路径不变。

共享函数在适配器本地构建并由宿主绑定校验；相同基础模型及 Machine 时钟配置复用函数表和绑定。直接 JIT 同步读写调用者的同一执行帧，沿用 dirty bits，并将函数读写集合纳入调用者的入口检查。不支持的调用使整条 JIT 指令在执行前回退，不在访存中间暂停、发布或重放。

独立 Chromium 首步探针（不纳入 A/B 计时）记录到两版均翻译 247 个块。块内 IR 从 **664,271 降至 456,806**；计入六个共享函数的 8,476 条 IR，合计 **465,282 条（−30.0%）**。157 个动态系统区调用点全部保留。探针结束时，直接程序覆盖 241/247 个已翻译块，含共享调用的块覆盖 75/77；快照未区分暂未纳入程序的块与直接编译拒绝的块。

Node.js 24.20.0、CPU 亲和性 `8,10,12,14`，按基线、候选、候选、基线各跑一组六轮，使用 `MICA_CT117E_M4_PACKAGE` 指定保存的发布器件包。每轮清屏均为 **104,338 次 WR 变化、52,169 次 GRAM 写入、2 帧**；至 440 ms 的总工作量一致。

| 360–390 ms 清屏                   |     基线 |      候选 |
| --------------------------------- | -------: | --------: |
| 两组合并，去首轮的墙钟中位数      | 29.20 ms |  39.11 ms |
| 两组合并，去首轮的进程 CPU 中位数 | 35.82 ms | 100.74 ms |
| 合并各组末两轮的墙钟中位数        | 28.64 ms |  35.29 ms |

候选修复了相同块无法跨实例复用绑定校验的问题，Node 暖轮到 10 ms 的建板加首步耗时随之恢复启动收益，但清屏中位数仍偏高。较快候选窗口仍能到约 29 ms，部分暖轮又回到 39–71 ms。

独立入口探针中，两版在清屏窗口内均覆盖 314 个 PC，逐轮均有 242 次直接尝试、62 次回退和 90 次直接截止，程序身份不变且没有新增构建。到清屏入口时，累计直接程序构建次数均为 27，当前程序的驻留分片数从 126 降为 120。另开 V8 采样的一组中，两版慢轮入口前 10 ms 都未采到 TurboFan 分片叶子，快轮则都有。采样组未重现无探针 ABBA 的差距，尚不足以归因。

板级回归覆盖 `STMIA` / `LDMIA` 顺序和写回、窄读取的 SysTick `COUNTFLAG` 读清、NVIC 优先级宽度掩码，并核对六种调用均能纳入直接程序。运行时回归另覆盖同帧内连续调用、状态和内存可见性、被观察的写入在入口回退。

## 分片布局重放

沿用 Node 清屏基准的原始固件与 10 ms 步长。独立记录第五轮和第六轮每次直接程序构建的分片 ID、分片顺序和 `case` PC 顺序，再用第六轮的共享处理体重放第五轮布局。重放只在基准加载模块时注入，不改生产源码。计时对照的两侧均走同一套重放代码：A 用第六轮自身布局，B 用第五轮布局；均不启用 V8 采样或窗口探针。

- 每轮至 440 ms 共构建 29 次直接程序。三种配置逐次的 PC 集合和续跑 ID 相同；第六轮自身与第五轮有 18 次布局不同，重放逐次恢复了第五轮的分片 ID 和有序分组。
- 清屏入口的 314 个 PC 中，81 个的同片 PC 集合改变。此前采样的三个主要热分片中，`119 → 113` 移出了 `0x08001036`，它在候选中与 `0x0800103c` 同片；`121 → 115`、`122 → 116` 的有序 PC 分组不变。后两片的生成源码除分片编号和常量池下标外相同。
- 清屏窗口的直接尝试、回退和截止次数不变，窗口内都不重建。每轮仍为 104,338 次 WR 变化、52,169 次 GRAM 写入、2 帧；至 440 ms 的总工作量、三帧的交付时刻及字节 SHA-256 也一致。

各六轮的初测（去掉首轮）中，A、B 的墙钟中位数为 **39.37 → 28.51 ms**，进程 CPU 中位数为 **101.07 → 35.78 ms**。差异主要来自 A 的第六轮再次变慢（70.54 ms）；两侧第 2、3 轮都慢，第 4、5 轮都在 30 ms 以内。因此另跑 ABBA 复核初测信号，而不把这一轮差异直接归因于布局。

ABBA 各组六轮，与前面的生产包对照使用同一 Node 版本和 CPU 亲和性。时间单位为 ms：

| 360–390 ms 清屏                   | A：候选布局 | B：第五轮布局 |
| --------------------------------- | ----------: | ------------: |
| 两组合并，去首轮的墙钟中位数      |       42.48 |         40.35 |
| 两组合并，去首轮的进程 CPU 中位数 |      105.05 |        102.89 |
| 合并各组末两轮的墙钟中位数        |       54.81 |         33.38 |
| 合并各组末两轮的进程 CPU 中位数   |      129.34 |         64.77 |
| 暖轮超过 45 ms                    |        5/10 |          3/10 |

正序组末两轮，A 为 28.33 / 70.92 ms，B 为 27.56 / 27.63 ms；反序则两侧都慢，A 为 71.63 / 38.70 ms，B 为 72.25 / 39.13 ms。**恢复布局没有稳定恢复清屏性能**：末两轮合并值改善，但正序看到的收益未在反序复现，不能把原退化单独归因于分片布局。

另跑一对 V8 采样组。两侧第 2、3 轮清屏的前 10 ms 均未采到 TurboFan 分片叶子，首次记录到新的 `stepShard` TurboFan 代码分别在 A 的 **25.32 / 15.07 ms**、B 的 **18.36 / 16.87 ms**。两侧第 4–6 轮的前 10 ms 都已有分片在 TurboFan 执行，且未复现无采样组最后两轮再次变慢的现象。采样能区分快慢轮，但还不能说明是什么触发了后期暖轮重新变慢。

诊断脚本、布局记录和原始日志保存在 `/tmp/opencode/ct117-shard-replay`。不保留生产重放补丁，也不扩大到非 GPIO 外设。

## 固定候选布局：清屏入口的 V8 层级

继续用第六轮发布模型和原有布局。独立诊断在进度 350、360、390 ms 查询三个主要热分片的 V8 优化状态；查询只读取函数状态，不强制编译，也不进入清屏计时。另开一组记录代码生成和去优化事件，不做定时采样。360 ms 时仍为第 27 次直接程序、120 个驻留分片、314 个 PC；清屏结束时程序对象不变。

两组状态探针和一组事件对照中，第 2 轮（71–73 ms）在入口没有 TurboFan 热分片，第 3 轮（38–42 ms）三个热分片在入口均为 Maglev、退出时均为 TurboFan；第 4–6 轮（28–30 ms）三个热分片在入口和退出均为 TurboFan。350 ms 时尚未建好包含这三个热分片的程序，不能用该点的函数状态推断入口曾经处于哪一层。

按 V8 脚本编号追踪第 3 轮：三个入口热分片沿用第 2 轮的脚本，三组事件记录均在入口前约 **430–449 ms** 看到三个分片的 TurboFan 循环内升层代码去优化。其中 `stepShard113` 为 PC 派发比较缺少类型反馈，`115/116` 为状态槽写入缺少键访问反馈。入口前约 **11–17 ms** 三者重新生成 Maglev 代码，入口后约 **15–26 ms** 再生成 TurboFan 代码。即使模拟器在清屏期间不重建程序，复用的 V8 脚本也可能在清屏前丢失已编译的优化代码。

其中两组事件记录只在清屏前后加时间标记，不读取函数状态或改动编译器；与两组无探针对照交替运行。四组均未重现第 5、6 轮再变慢，末两轮墙钟 **28.08–28.94 ms**、进程 CPU **28.09–28.95 ms**。因此已复现的是第 3 轮去优化和重新升层，后期慢轮仍未归因；不能据此改写热路径或通过稳态验收。下一步优先在能复现后期慢轮的固定布局下，只抓热分片入口前后的去优化事件。

诊断脚本与原始日志保存在 `/tmp/opencode/ct117-clear-tier-entry`；未改生产代码或固件。所有组仍通过清屏和 440 ms 总工作量校验。

## 后期慢轮复现

固定重放第六轮自己的布局，沿用相同发布模型、Node 版本、CPU 亲和性和 10 ms 步长。先按「无探针 → 仅 `--trace-deopt` → 仅 `--trace-deopt` → 无探针」各跑六轮；第 5、6 轮均为 27.38–29.22 ms，两个追踪组在第 4–6 轮没有记录到热分片去优化。随后延长同一进程内的独立建板轮数，保持单轮调度和布局不变。第一组无探针的第 5、6 轮重新出现 **71.39 / 38.53 ms** 的清屏窗口，进程 CPU 分别为 **161.73 / 100.66 ms**，说明晚到的慢轮并非单纯墙钟抖动。

16 轮组均出现「额外慢一轮，下一轮仍偏慢，再回到约 28 ms」的序列，首次出现轮号不固定：

| 组                     | 轮号 | 清屏墙钟（ms） | 清屏进程 CPU（ms） |
| ---------------------- | ---: | -------------: | -----------------: |
| `control-3` 无探针     |  5/6 |  71.39 / 38.53 |    161.73 / 100.66 |
| `deopt-3` 仅去优化文本 |  8/9 |  66.88 / 37.93 |     145.64 / 98.55 |
| `events-1` V8 代码事件 | 9/10 |  73.67 / 38.99 |    162.33 / 101.28 |
| `control-4` 无探针     |  4/5 |  70.69 / 37.99 |    161.93 / 100.02 |

- `deopt-3` 第 8 轮进入清屏前，三个热分片各有 Maglev 代码因 `embedded weak objects cleared` 被标记失效；同一轮、同一 SFI 后续有新的优化代码因类型反馈不足去优化，清屏窗口内 `113/116` 还有 TurboFan 去优化。这批失效记录标的是 Maglev，不是此前快轮的 TurboFan 代码。
- `events-1` 第 9 轮仍使用脚本 `1011/1013/1014`，未记录这三个分片的新字节码脚本。入口前已经重新生成 Maglev OSR（循环内升层）代码并出现去优化；入口后 **18.53–31.45 ms** 才生成新的 TurboFan OSR 代码。第 10 轮入口前生成 Maglev，入口后 **16.73–18.09 ms** 重新生成 TurboFan（这组不是 OSR）；第 11 轮回到 **28.24 ms**。

同一脚本乃至同一 SFI（共享函数元数据）不表示复用了同一个 JS 函数对象，更不表示仍在执行同一份优化代码。每轮重新建板，分片编译器每次调用生成工厂时会返回新的函数对象。两个进程的日志分别支持「弱依赖失效」和「同脚本重新升层」，不能直接串成一条因果链。四组均通过清屏和 440 ms 总工作量校验。

### 同进程对齐主 GC 与重新升层

再跑各 16 轮 ABBA，无探针对照与同时开启 `--trace-gc-nvp --trace-gc-ignore-scavenger --trace-deopt --log-code --log-deopt` 的事件组各两组。沿用同一重放计划，在事件组标记每轮开始、清屏入口和退出。不做定时采样、强制 GC 或强制升层。

| 组                 | 慢轮/次轮 | 清屏墙钟（ms） | 清屏进程 CPU（ms） | 慢轮入口前主 GC 暂停（ms） |
| ------------------ | --------: | -------------: | -----------------: | -------------------------: |
| `control-5` 无探针 |       6/7 |  74.51 / 37.87 |     164.65 / 99.11 |                          — |
| `gc-1`             |       7/8 |  75.62 / 56.97 |    168.40 / 104.12 |                       42.3 |
| `gc-2`             |       8/9 |  71.77 / 38.71 |     160.83 / 99.99 |                       36.7 |
| `control-6` 无探针 |       6/7 |  70.40 / 38.36 |     160.75 / 99.83 |                          — |

`gc-1` 和 `gc-2` 中，前一轮均在 29 ms 内完成。主 GC（`gc=mc`）分别在第 7、8 轮进入清屏前结束；对应慢窗内未记录主 GC 暂停。三个热分片仍沿用原脚本及 SFI，入口前重新生成 Maglev OSR 并因类型反馈不足去优化，入口后约 **18–33 ms** 才陆续生成 TurboFan OSR。两个慢轮的日志都没有热分片的 `embedded weak objects cleared` 标记。因此，主 GC 与随后重新升层的关联在同一进程内复现，但不能解释成「GC 暂停占用了清屏窗口」或「已确认此前的 TurboFan 快路径被该事件直接标记失效」。

按生成脚本过滤同名的 `run` 函数：两组慢窗内也各有直接程序派发器生成两份 TurboFan 代码并去优化一次；前一轮窗口内没有这类事件。三个分片不是唯一重新升层的生成函数。

另开两组记录 V8 反馈向量，仅用于核对身份。`feedback-2` 第 6 轮入口前发生主 GC（34.7 ms）；慢轮沿用三个热分片的 SFI，但首次 Maglev OSR 编译记录中的反馈向量地址均不同于第 3 轮生成普通 TurboFan 代码时的地址，调用计数由 `3975/5841/11481` 降至 `1165/1961/1163`（按 `113/115/116` 顺序）。第 7 轮生成 Maglev 和 TurboFan 时继续使用第 6 轮记录的向量地址。GC 可移动对象，不能仅凭地址变化判断向量被替换；计数降低和再次出现类型反馈不足使「跨轮反馈未保住」比「同一份 TurboFan 代码被直接标记失效」更值得优先验证。反馈日志明显扰动计时；`feedback-1` 第 2 轮后没有主 GC，也没有复现同样的慢轮序列，不用这两组做速度验收。

同版本 V8 的 `Compiler::GetFunctionFromEval` 可以在命中 SFI 时没有可复用的反馈单元，符合脚本不换、类型反馈重新积累的观察。

### 仅保留工厂的对照未通过

只在诊断重放里将 `113/115/116` 最近生成的三个工厂各保留一个强引用；仍照常调用 `new Function`，没有复用工厂对象、旧板或已绑定的分片。无 V8 探针 ABBA 各 16 轮，第 4–16 轮的墙钟/进程 CPU 最慢值分别为：两个对照 **72.12/163.71、66.19/158.99 ms**，两个保留组 **37.84/99.09、72.03/162.42 ms**。第一组未再出现约 70 ms 的慢窗，反序试验仍在第 6、7 轮出现 **72.03 / 38.75 ms**。

在带主 GC 追踪的保留组，32.0 ms 的自然主 GC 在第 7 轮清屏前结束；该轮清屏仍为 **71.80 ms**、进程 CPU **153.69 ms**。三个分片仍是原脚本，首次生成新的 TurboFan OSR 代码仍在入口后 **18.42–31.34 ms**。仅持有三个工厂不能稳定消除慢轮；结果不等于已经验证过直接复用工厂。若继续验证，先按完全相同的生成源码复用同一个工厂对象，仍用本轮常量创建新分片闭包，并单独追踪派发器 `run`，避免把分片与派发器的重新升层混为一谈。

各组均通过逐轮布局、LCD 总线工作量及帧数校验。最小对照未通过，不扩大到逐帧哈希或生产浏览器验收。脚本和原始日志在 `/tmp/opencode/ct117-late-clear`，结果见 `late-summary.log`、`gc-phase-summary.log`、`gc-events-summary.log`、`feedback-summary.log` 和 `hold-summary.log`。未改生产代码，性能基线仍为 `34c09f3`。

### 复用同源码的生成工厂

与仅持有引用不同，这组在诊断重放中让 `113/115/116` 的生成源码与参数签名完全相同时返回同一个工厂对象。每个分片最多缓存一个工厂，源码变化就替换；仍调用工厂，以本轮常量和运行时辅助函数创建新的分片闭包。其他分片和派发器的生成路径不变。

派发器按生成源码的 PC → 分片索引映射匹配清屏入口的 314 个 PC，不按函数名 `run` 混合统计。重新分析 `gc-1`、`gc-2` 和 `holdgc-1` 的后期慢轮：入口派发器在窗口开始前 **14.64–20.13 ms** 已生成 TurboFan 代码，进入窗口后 **24.78–26.92 ms** 在调用点因反馈不足去优化。该调用点处理 PC `0x00020050`：`D116` 是派发数组下标，实际指向 `stepShard117`，不属于三个被复用的热分片。之后同一入口派发器才再次生成 TurboFan 代码。三个分片的重新升层与派发器的这次去优化应分别计数。

| `control-9` 原生成路径  |       27.95 / 73.31 |           27.95 / 161.88 |
| `reuse-1` 复用工厂      |       27.72 / 30.35 |            27.71 / 51.02 |
| `reuse-2` 复用工厂      |       28.12 / 31.10 |            28.12 / 50.83 |
| `control-10` 原生成路径 |       28.52 / 70.57 |           28.82 / 158.97 |

两组对照都在第 6、7 轮重现慢窗；两个复用组未重现约 70 ms 的慢窗，但仍有 CPU 超过 50 ms 的轮次。另开 16 轮正确性对照，三个工厂各有 1 次未命中、15 次命中；两侧清屏程序在窗口内均不变，直接尝试/回退/截止次数为 242/62/90，仍有 104,338 次 WR 变化、52,169 次 GRAM 写入及 2 帧。至 440 ms 的总工作量、三帧逐字节 SHA-256 和交付时刻均与记录一致。

`gc-4` 与 `reusegc-1` 均在第 7 轮清屏前发生自然主 GC（36.2 / 49.4 ms）。清屏墙钟分别为 **72.05 / 30.42 ms**，进程 CPU 为 **153.38 / 40.74 ms**。对照在慢窗内重新生成三个热分片的 TurboFan OSR 代码；复用组没有对应的热分片代码生成或去优化事件，但入口派发器仍在同一个 `D116` 调用点去优化并再次升层。这表明派发器仍有额外成本，但单独出现该事件并不必然产生约 70 ms 的慢窗；也不能把复用组的结果归因于跳过主 GC。

第二组固定布局追踪 `reusegc-2` 在第 5 轮清屏前发生 35.4 ms 自然主 GC。清屏为 **29.82 ms / 44.64 ms**（墙钟 / 进程 CPU）；仍未记录三个热分片重新编译或去优化。入口派发器在清屏内生成 TurboFan OSR，随后在 `D116` 去优化并再次升层。两次追踪都没有复现对照的后期慢窗。

### 有界工厂缓存试验

首版按完整生成源码和固定参数签名查找工厂，LRU 限 256 项、4 Mi UTF-16 代码单元，不共享已绑定的闭包。与 `34c09f3` 的无探针六轮 ABBA 中，去首轮的清屏墙钟中位数 **29.92 → 31.50 ms**，进程 CPU **36.36 → 37.95 ms**，未过。独立计数显示，每轮产生 137 个工厂、生成源码共 5,711,846 个代码单元；连续三轮缓存全部未命中。重复按相同顺序生成源码时，工作集大于缓存，先生成的分片持续淘汰后生成的分片。

下一版总源码预算仍为 4 Mi 代码单元，改为最多保留 128 项，单项超过 64 Ki 代码单元时不进缓存。独立计数中原有的 22 个大工厂占约 1.93 M 代码单元，其余 115 个工厂共约 3.78 M，能在同一工作负载内同时保留。不按板型、分片编号或 PC 特判；预算限制缓存保留的源码，不代表 V8 代码和反馈向量的总内存。

新版缓存与 `34c09f3` 各跑两组 16 轮，无 V8 探针、无布局重放，顺序为基线 → 缓存 → 缓存 → 基线。基线使用 `34c09f3` 的编译器、运行时和发布器件包；候选使用第六轮共享访存和有界工厂缓存。结果合并如下（ms）：

| 360–390 ms 清屏                  |      `34c09f3` | 带缓存的第六轮 |
| -------------------------------- | -------------: | -------------: |
| 去首轮的墙钟中位数 / 最大值      |  29.01 / 72.65 |  28.33 / 43.65 |
| 去首轮的进程 CPU 中位数 / 最大值 | 30.20 / 201.96 | 28.95 / 144.10 |
| 第 4–16 轮墙钟最大值             |          72.19 |          30.30 |
| 第 4–16 轮进程 CPU 最大值        |         161.34 |          50.70 |

两侧共 64 个计时轮均通过 LCD 工作量校验。独立正确性审计各跑六轮，窗口内程序不重建，覆盖同一批 314 个 PC，直接尝试/回退/截止仍为 242/62/90；104,338 次 WR、52,169 次 GRAM 写入和 2 帧均不变。推进到 440 ms 后，两侧在 380、390 和 410 ms 交付的三帧 SHA-256 逐一相同。
