# 直接后端重建成本：冷启动与稳态的共同瓶颈

- 日期：2026-11-13
- 范围：`packages/compiler/src/direct-jit.ts`、`packages/simulator/src/runtime/jit.ts`
- 复现对象：`examples/ili9325/test/fixtures/HAL_06_LCD.bin`（裸 MCU、80 MHz、`execution: 'throughput'`）
- 关联文档：缺陷与口径见 `docs/stm32g431rbt6-issues.md`，块结构见 `docs/mcu-jit-block-inflation.md`

本文只记录本轮对**重建开销**的定位结论与实测数据。2.2、2.3、2.5 三节修正了
`docs/stm32g431rbt6-issues.md` 中已被测量推翻的三处结论，其余读数不重复维护。

## 1. 结论摘要

1. **整程序重建不只是冷启动瓶颈，也是稳态瓶颈**：实测稳态窗口里 68% 的 CPU 花在 5 次重建上。
2. **重建贵在发射器自身，不在 V8 解析**：CPU 采样里发射相关函数约占 80%，V8 编译生成源码不到 2%。
3. **重建成本与「新增几块」无关，只与「总块数」线性相关**：约 1.05 ms/块，411 块 448 ms。
   `stride` 摊薄的只是重建**次数**，单次重建的**规模**没有被摊薄。
4. **发布读数是三轮最小值**，首次运行（用户第一次跑）冷启动 7.0–7.2 s，是发布读数的 7 倍。
5. 次要瓶颈：每次 `program.run` 有约 3–7 µs 的固定成本（94 个 state 全量读入、dirty 位图清零、
   94 个写回槽逐个检查），只在宿主步长极小时才显著。
6. 文档 2.5 的「第 1 项之外的优化只影响冷启动」不成立——第 1 项是唯一同时影响两个窗口的项；
   2.5 列出的三项体积问题只在翻译期付一次，命中在重建成本内部，没有独立收益。

## 4. 瓶颈一：整程序重建

`jit.ts:240` 的 `runDirect` 在「当前程序未覆盖目标 PC」或「攒够 stride」时调用
`compileDirectJit`，而 `compileDirectJit`（`direct-jit.ts:174`）总是**遍历全部块**重新发射。
`jit.ts:29-33` 的 `DIRECT_REBUILD_LINEAR_LIMIT` / `DIRECT_REBUILD_MIN_BLOCKS` /
`DIRECT_REBUILD_PATIENCE` 控制的只是触发时机。

### 4.1 冷启动 CPU 采样（5684 个样本）

| 占比     | 函数                                               | 位置                         | 性质           |
| -------- | -------------------------------------------------- | ---------------------------- | -------------- |
| 16.4%    | `rewrite`（正则把 `vN` 换成物理槽）                | `direct-jit.ts:821` 内部     | 发射           |
| 9.9%     | GC                                                 | ——                           | 发射的分配压力 |
| 9.0%     | `compact`（活跃区间扫描）                          | `direct-jit.ts:821`          | 发射           |
| 8.7%     | `names`（逐行正则提取 `vN`）                       | `direct-jit.ts:824`          | 发射           |
| 8.1%     | 槽分配遍历                                         | `direct-jit.ts:821` 内部     | 发射           |
| 8.1%     | `operation`                                        | `direct-jit.ts` 的 IR 访问器 | 发射           |
| 8.1%     | 行遍历 / 收集                                      | `direct-jit.ts:821` 内部     | 发射           |
| 6.8%     | `Instruction.compile`                              | `direct-jit.ts`              | 发射           |
| 3.6%     | `region`                                           | `direct-jit.ts` 的 IR 访问器 | 发射           |
| 3.0%     | `compileDirectJit`                                 | `direct-jit.ts:174`          | 发射           |
| 2.3%     | `countOperations`                                  | `direct-jit.ts`              | 发射           |
| **1.7%** | **V8 编译生成源码**（`(program)`、`compiledBody`） | ——                           | 解析           |

发射器合计约 **80%**，GC 9.9%（主要来自逐块生成字符串与 Map），V8 解析 1.7%。
`stm32g431rbt6-issues.md` 2.3 把原因归给「让 V8 重新解析全部已编译块」，与采样不符：
**重建的成本在生成源码这一侧，不在解析那一侧。**

`compact` 的内部实现值得单列：它对每个块把 `prefix + suffix` 全部行做两遍正则
（`line.match(/\bv\d+\b/g)` 与 `line.replace(/\bv(\d+)\b/g, ...)`），并用 `Map<number, ...>`
记录每个虚拟槽的定义/首次使用/末次使用。411 个块、353 个可编译块共发射 164,076 条语句，
每次重建都要把这些语句重新正则扫一遍。

### 4.2 编译成本随块数线性

直接调用 `compileDirectJit`（V8 已热，同一进程内三轮取最小）：

| 块数  | 17      | 48      | 77      | 159      | 273      | 353      | 411          |
| ----- | ------- | ------- | ------- | -------- | -------- | -------- | ------------ |
| 耗时  | 15.8 ms | 43.4 ms | 69.7 ms | 173.7 ms | 306.1 ms | 378.2 ms | **447.8 ms** |
| ms/块 | 0.9     | 0.9     | 0.9     | 1.1      | 1.1      | 1.1      | 1.1          |

线性、无拐点。**每次重建都要为「已经编译过的块」再付一次这个成本**，与本次新增了几块无关。

同一份程序的发射规模（`emitStats`）：

| 指标                 | 值                                                     |
| -------------------- | ------------------------------------------------------ |
| 可编译块             | 353                                                    |
| IR 操作 / 含嵌套操作 | 5,433 / 273,233                                        |
| 发射语句             | 164,076                                                |
| 语句 / 操作          | 30.2                                                   |
| 被折叠掉的操作       | 88,106                                                 |
| `select` 块          | 667                                                    |
| 最坏块               | pc `0x20040`：9 个操作 → 1,994 条语句（221.6 条/操作） |

### 4.3 稳态归因（10 ms 步长，与 `hal-bench.ts` 同口径）

```
[STEADY-ATTRIB] totalMs 3481.7  rebuildCount 5
                rebuildWindowMs 2370.2  rebuildSharePct 68
```

逐个 10 ms 步：

| 推进到     | CPU           | 重建数 | 当时的块数 |
| ---------- | ------------- | ------ | ---------- |
| 60.2 ms    | 417.7 ms      | 1      | 277        |
| 70.2 ms    | 411.1 ms      | 1      | 279        |
| 80.2 ms    | 1015.4 ms     | 2      | 283        |
| 130.2 ms   | 526.0 ms      | 1      | 411        |
| 其余 18 步 | 每步 40–62 ms | 0      | 411        |

5 次重建合计 2,370 ms，占该窗口 3,482 ms 的 **68%**。折算到发布基线（稳态 2,709 ms、
同样 5 次重建、末次 411 块），重建占比只会更高——按 448 ms/次估算约 2,250 ms。

**结论：稳态的 12× 慢于实时里，大部分不是执行指令，而是重建。** 这个结论与
`stm32g431rbt6-issues.md` 2.5 的「第 1 项之外的优化只影响冷启动，对稳态没有可测收益」直接冲突：
第 1 项本身就是稳态的最大项。

### 4.4 首次运行与发布读数

同一进程内连续三轮冷启动（每轮新建 board，器件翻译缓存模块级共享）：

| 轮次    | 冷启动 0 → 200 µs                       |
| ------- | --------------------------------------- |
| 第 1 轮 | **7,202 ms**（另一次独立测量 7,036 ms） |
| 第 2 轮 | 1,223 ms                                |
| 第 3 轮 | 961 ms                                  |

发布读数是三轮最小值，因此记录的是「发射器已被 V8 优化之后」的成本。用户第一次跑这份固件
看到的是秒级的 7 s。同一现象在小程序上也存在：首块翻译的 `runUntil` 花了 180 ms（17 块），
随后同样规模的块只需十几毫秒。

**未隔离**：这 6 s 的差额中，V8 对发射器分层优化的贡献与「器件代码自身首次编译」的贡献没有分开测量。

### 4.5 `stride` 为什么没有解决问题

`jit.ts:262-268` 的 stride 在块数超过 16 后取 `max(64, 已编译块数)`，所以每次重建要等新增
64 个块以上（大程序更久）。这把重建次数从「每块一次」（43 次 / 1.67 s）压到 25 次，但没有改变
**每次重建都重编译全部块**这一事实：块越多，单次重建越贵，次数越少，总量仍然是 O(块数²) 量级。

实测块数增长与重建次数（冷启动窗口 0 → 200 µs，5 µs 步进）：

| 推进到   | 累计 CPU | 重建数 | 块数 |
| -------- | -------- | ------ | ---- |
| 5 µs     | 180 ms   | 16     | 17   |
| 25 µs    | 271 ms   | 17     | 159  |
| 50 µs    | 1,326 ms | 21     | 192  |
| 85 µs    | 2,429 ms | 25     | 228  |
| 155 µs   | 2,785 ms | 26     | 273  |
| 115.3 ms | 8,139 ms | 37     | 411  |

（该组用 5 µs 步进，比发布口径更细，累计 CPU 偏高；块数与重建数的对应关系仍可比。）

## 5. 瓶颈二：每次 `program.run` 的固定成本

`jit.ts:388-391` 在每次 `run` 前做两件全量工作：把程序声明读过的 **94 个 state**逐个
`instance.states.get(name)` 写进 frame 数组，并把 `stateDirty` / `memoryDirty` 位图清零；
`jit.ts:402-410` 在 `finally` 里逐个检查 **94 个写回槽**的 dirty 位。

在 411 块全部翻译完成后推进同样 220 ms（无重建、无回退）：

| 宿主步长        | CPU                  | `program.run` 次数 |
| --------------- | -------------------- | ------------------ |
| 单次推进 220 ms | 877 ms（含一次重建） | 2                  |
| 100 ns          | 14,435 ms            | 4.40 M             |
| 10 ns           | 37,632 ms            | 11.76 M            |
| 1 ns            | 77,832 ms            | 11.76 M            |

折合约 **3–7 µs / 次 `run`**。发布基线用 10 ms 步长，因此读数没有被这项污染；但逐步调试、
逐帧推进、外部事件密集的板上，这项会放大一到两个数量级。

## 6. 瓶颈三：回退与生成代码热路径

- `directFallbacks` 稳态占 2,265 次（总计 4,702）。每次回退是「直接尝试 → 解释器派发 → 再入队」，
  一次回退抵消多条指令的直接执行收益。
- 稳态采样里，`run` dispatcher 占 21.4%（两个生成程序各一份），`stepShardN` 分散约 25%，
  `view`（`direct-jit.ts:119` 的 `DataView` WeakMap 查找）占 3.3%——每次宽访存都查一次缓存，
  可以改成 frame 持有 `DataView` 引用。`readSample`（`instance.ts`）占 1.4%。
- 稳态采样里 direct-jit 发射函数仍占约 27%，与 4.3 的 68% 互相印证（采样窗口包含重建步）。
- `stm32g431rbt6-issues.md` 2.5 的三项体积问题（引脚意图 `select` 链、`SERVICE_WRITE` 三份写路径、
  动态基址多寄存器逐字判定）在稳态不再出现：它们只在首次翻译时付一次，成本已经包含在 4.2 的
  1.05 ms/块里，没有独立收益。

## 7. 与 `stm32g431rbt6-issues.md` 的三处偏差

| 节  | 原文结论                                | 实测                                                                   |
| --- | --------------------------------------- | ---------------------------------------------------------------------- |
| 2.3 | 重建让「V8 重新解析全部已编译块」       | V8 解析 1.7%；发射器约 80%                                             |
| 2.5 | 第 1 项之外只影响冷启动，稳态无可测收益 | 第 1 项占稳态 68%，是唯一双收益项                                      |
| 2.2 | 稳态 0.08× 实时                         | 该值含重建；扣除重建后的执行速率需按重建次数折算，不能直接读作执行速度 |

## 8. 修复接缝与预期收益

`Instruction`（`direct-jit.ts` 的 `class Instruction`）是 per-PC 的纯编译结果，只依赖
块 IR 与 binding；`stepShardN` 已经是独立顶层函数（`shardProgram`，`direct-jit.ts:459`）。

**最小改动：按 PC 缓存 `Instruction`。** 重建时只 `compile()` 新增块，复用旧块，再拼装 shard。
剩余成本是拼行 + `new Function`（约 25–30%）。411 块重建预计 448 → 约 130 ms；稳态从 3,482 ms
降到约 1,600 ms。三条约束必须同时满足：

1. **常量索引要跨重建稳定**。`literal()` 走 `capture()` 向共享的 `constants` 数组**追加**，
   `C[i]` 是数组下标；复用旧 `Instruction` 时若换用新数组，索引会错位。缓存必须连同常量表一起
   持有，或在拼装时给每块常量表加偏移。
2. **`delayLoops` 会改变 `guard`**。它参与程序缓存 key（`runDirect` 里的 `JSON.stringify`），
   所以延时环集合变化时，命中缓存的块也要重发 `guard`。
3. **binding 的索引在 revision 内必须稳定**。state/memory 名字来自 `instance.states.keys()`，
   只增不改，已有下标不会移动，因此同一 revision 内可以跨重建复用。

**完整增量：shard 常驻。** 让每个 `stepShardN` 作为独立函数对象常驻，新增块只编译新 shard，
`run` 的 dispatcher 按 pc 区间扩表，重建成本可压到接近 0。这需要改 `DirectJitProgram` 的结构，
但语义上可行：`pcs` 已经是只增不改的集合（`jit.ts:254-258` 的注释即以此为前提）。

**次要项**：`view()` 改为 frame 持有 `DataView`；`run` 的 state 同步改为按版本号增量刷新，
只在细粒度推进时才需要。

## 9. 复现方式与未验证项

本次分析用的临时脚本（`bench/_profile.test.ts`、`_attrib.test.ts`、`_curve.test.ts`）在取数后
已删除，未入库。复现需要四件事，全部只用公开接口或包内导出：

1. **基线**：`vitest run --config vitest.perf.config.ts bench/hal-throughput.test.ts`。
2. **重建成本曲线**：从 `board.jits[0].cache` 取块，直接调 `compileDirectJit`，按 17/48/77/159/273/353/411
   取前缀，`process.cpuUsage` 计时、三轮取最小。
3. **稳态归因**：先跑到 200 µs 与 220 ms 完成全部翻译，再按 10 ms 步长推进，逐段记录
   `directStats.directCompiles` 与 `process.cpuUsage`。
4. **CPU 采样**：`node:inspector/promises` 的 `Profiler.start/stop`，冷启动用 100 µs、稳态用 20 µs
   采样间隔，按 `hitCount` 汇总 `callFrame.functionName`。

未验证项：

- 4.4 中首次运行的 6 s 差额没有拆分到「发射器分层优化」与「器件代码首次编译」。
- 稳态归因只做了一次 10 ms 步长的完整窗口（3,482 ms），发布基线是三轮最小值（2,709 ms）；
  两者差异来自 V8 预热，未进一步隔离。
- 第 8 节的收益是估算值，尚未实现验证。
