# STM32G431RBT6 稳态性能瓶颈快照

- 日期：2026-11-14
- 对象：`examples/ili9325/test/fixtures/HAL_06_LCD.bin`
- 条件：STM32G431RBT6、裸 MCU、80 MHz、`execution: 'throughput'`
- 口径：先推进 220 ms 完成翻译与程序重建，再对后续 220 ms 以 10 ms 切片采样
- Profiler：`node:inspector`，25 µs 采样
- 关联：冷启动与首次运行归因见 `docs/stm32g431rbt6-execution-bottlenecks.md`

## 1. 结论

当前稳态瓶颈已经不再是 HAL_Delay 忙等。HAL_Delay 时间事件轮询后，主要成本集中在：

1. **shard 碎片化与大 dispatcher 路由**：`run` 占约 **31.4%** self samples；
2. **GPIO 写入链**：GPIO guest 写块、service、电气 helper 合计约 **53–54%**；
3. **热点单指令 GPIO 写块的通用守卫**：9 个热点 PC 占约 **45%** 块入口；
4. **Direct fallback 快速路径缺失**：稳态 1,432 次 direct 调用中约 1,416 次回退。

GC 已降至约 **0.65%**，电气求解和 boundary 均低于 1%，不再是主瓶颈。

## 2. CPU 归因

3207 个稳态 self samples：

| 类别                      |       占比 |
| ------------------------- | ---------: |
| `run` dispatcher          | **31.37%** |
| GPIO guest 写 shard       | **24.95%** |
| GPIO service shard        | **17.87%** |
| GPIO/电气 helper          | **10.79%** |
| JIT runtime / `runDirect` |  **8.29%** |
| 其他 simulator            |      2.78% |
| 其他生成代码              |      2.09% |
| Direct 数据 helper        |      1.22% |
| GC                        |      0.65% |

GPIO 相关的 guest 写块、service 和 helper 合计约 **53–54%**；dispatcher 与 JIT runtime 合计约 **39–40%**。

## 4. 主要瓶颈

### 4.1 Shard 碎片化与 dispatcher

- `run` dispatcher 是最大单项，占 **31.37%**。
- 已封闭 shard 不再吸收后续翻译出现的相邻 PC，导致连续 GPIO 写 PC 落入多个小 shard。
- 跨 shard 切换虽然仍在同一个 `run` 循环内，但每次都要经过 411 个 PC case 的 dispatcher。
- 可争取方向：热 shard compaction、相邻 shard 合并、PC 到 shard 的直接映射，或返回下一 shard 句柄以跳过全局 PC 查找。
- 若 dispatcher 成本下降 30–50%，稳态总 CPU 预计下降约 **9–16%**。

### 4.2 GPIO service

- GPIO service 入口约 **109 万次**，占全部块入口约 **40%**。
- GPIOB service 约 95.3 万次，GPIOC service 约 13.7 万次。
- 当前 service 同时承担 ODR、BSRR、BRR、MODER、OTYPER、PUPDR、AFR 等路径，热点主要是 BSRR/BRR 输出写。
- 可争取方向：
  - 按 BSRR、BRR、ODR、配置写拆分 service；
  - 输出 service 去掉无关配置寄存器分派；
  - 删除冗余 `gpioWrite` 状态，仅以 `serviceMask` 表示待服务；
  - 对固定 GPIO 写生成更紧凑的 guest 块。
- service 与电气 helper 合计约 28.7%，现实可争取下降 15–25%，对应总收益约 **4–7%**。

### 4.3 热点单指令 GPIO 写块

- 9 个热点 GPIO 写 PC 各约 13.6 万次入口，但每条块只执行少量 guest 工作。
- 生成代码仍包含 write barrier、PC/dirty 写入、`pendingPs` 累加、`serviceMask` 判断与路由树。
- 可争取方向：为固定 `str` GPIO 写生成专用模板，减少局部槽、不必要的中间值和通用服务判定。
- 预期需微基准确认，现实目标约 **3–6%** 稳态提升。

### 4.4 Direct fallback

- 稳态 1,432 次 direct 调用中约 **1,416 次 fallback**。
- 回退主要集中在 `0x20000` service tick 和 `0x8000470` HAL_GetTick，各约 708 次。
- 这些 PC 位于 direct program 的 `pcs` 集合中，但执行后仍返回 `fallback`。
- 可争取方向：在 direct 入口前增加 eligibility 快速判定，或明确标记不可直接执行的 service/barrier PC。
- 与 dispatcher 优化合并后，预计约 **2–5%** 收益。

## 5. 已排除项

- HAL_Delay/HAL_GetTick 忙等：动态入口占比低于 **0.1%**；
- GC：约 **0.65%**；
- 电气求解本身：低于 1%；
- boundary、事件队列与发布路径：合计约 2–3%。

## 6. 优化优先级

1. **热 shard compaction 与 dispatcher 路由**：单项最大，且属于通用 JIT 收益；
2. **GPIO 输出 service 拆分与精简**：器件侧最大收益；
3. **单指令 GPIO 写块专用发射**：进一步压缩热点 guest 代码；
4. **Direct fallback 快速判定**：作为 dispatcher 优化的补充。

当前不应继续优先投入 HAL 等待链和 GC。

## 7. 测量注意

- 百分比是 profiler self samples，不是墙钟占比；
- profiler 会增加绝对耗时，读数用于相对归因；
- 稳态窗口使用 10 ms 宿主切片，包含每片 `program.run` 的固定进入成本；
- 精确值随 Node/V8、宿主和代码版本变化，以 `bench/hal-throughput.test.ts` stdout 为准。
