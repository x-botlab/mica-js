# STM32G431RBT6 稳态性能瓶颈快照

- 日期：2026-11-14
- 对象：`examples/ili9325/test/fixtures/HAL_06_LCD.bin`
- 条件：STM32G431RBT6、裸 MCU、80 MHz、`execution: 'throughput'`
- 口径：先推进 220 ms 完成翻译与程序重建，再对后续 220 ms 以 10 ms 切片采样
- Profiler：`node:inspector`，25 µs 采样，2,061 个 self samples
- 关联：冷启动与首次运行归因见 `docs/stm32g431rbt6-execution-bottlenecks.md`

## 1. 结论

最新稳态已经消除 GPIO service 与 HAL_Delay 忙等，主成本回到两类结构性工作：

1. **GPIO 边沿块与 dispatcher 往返**：8 个 LCD GPIO 边沿块合计约 34.6% self samples，
   `run` dispatcher 约 24.4%；
2. **引脚 intent 与电气 helper**：约 11.2%，其中 `VDD1` 采样仍是最贵的单次宿主调用之一；
3. **Direct runtime / JIT host bridge**：约 10.4%；
4. **GC**：约 3.7%，不再是主瓶颈。

一个重要修正是：**不能为了减少块入口把多个 GPIO 翻转合进同一个基本块**。宿主电气求解只在
块边界运行，合块会吞掉 LCD 的 WR 低→高脉冲。最终实现让静态 BSRR/BRR 写仍在 Guest 块内生成
intent，但在“可能改变引脚”的写之后收块；`examples/ili9325/test/joint.test.ts` 的真实
MCU + ILI9325 联合测试据此恢复通过。

| 引脚/电气模型 helper                 |          230 | **11.16%** |
| Direct runtime / JIT host bridge     |          214 | **10.38%** |
| GC                                   |           77 |  **3.74%** |
| 其他生成代码、存储 helper 与调度杂项 |          324 |     15.72% |

GPIO 相关生成块 + 电气 helper 合计约 **45.8%**；dispatcher 与 Direct runtime 合计约

service。

## 4. `0x08001104..0x08001152` 的实际生成形态

### 4.1 为什么不是单块

该区间包含 7 次 GPIOB 写，其中只有 4 次真正改变 ODR。若全部合进一个块，宿主只能在块尾求解
一次，4 个脉冲会被折叠成最终电平，真实 ILI9325 收不到 WR 边沿。最终按“每个可能改变引脚的
静态写后收块”拆成 8 个块：

- `0x08001104` 块：**36,591 字符 / 1,832 行 JS**；
- 8 个边沿块合计：**251,291 字符 / 12,328 行 JS**。

字数只用于和同一生成器比较；V8 的实际执行成本以窗口 CPU 与 profiler 为准。

### 4.2 运行时冗余检查

- 每个 220 ms 无重建窗口执行 135,999 轮 LCD 写序列；
- `F.host.sample('VDD1')` 调用 **545,221** 次，约 **4.01 次/轮**；
- `F.host.intent(...)` 调用 **545,911** 次，约 **4.01 次/轮**；
- ODR state / periph 映像写各 **544,765** 次，约 **4.01 次/轮**。

因此当前不是“每个有效翻转采样一次”，而是“每个含翻转的边沿块采样一次”。3 次
`changed === 0` 的写不会采样，也不会提交 ODR；它们不会贡献这 4 次调用。保留每个边沿块一次
采样是必要的：宿主动作和电气求解只能在块边界观察到中间电平。

曾尝试在同一块内共享 VDD/ODR 并做块尾单次提交；静态代码确实缩短，但会重新吞掉 GPIO 脉冲。
在保留 `boundaryAfter` 后，块内已不存在多个有效翻转可共享，该缓存只会增加局部槽与分支，实测
`shards` 从 71 增至 72、无重建最好值从 163 ms 退化到 175 ms，故最终删除。

## 5. 当前主要瓶颈与优先级

1. **GPIO 边沿块内部数据通路**（34.6%）：后续可继续压缩 `emitPinIntent` 的寄存器快照与
   `select` 树，但不能跨过电气边界合并有效翻转。
2. **dispatcher / shard 路由**（24.4%）：8 个边沿块分散在 `stepShard59–61`，跨 shard 后仍要
   经过 PC switch。可优先做热 shard compaction 或返回下一 shard 句柄。
3. **Direct host bridge**（约 10.4%）：`sample`、`resistor`、`intent`、状态/内存 helper
   仍是每个边沿的固定成本。
4. **GC**（3.7%）：比旧快照低，但仍可通过减少生成源码临时对象继续改善。

### 6.3 探索性合块结果（不可采用）

把整段 33 条指令和连续 GPIO 写全部合进一个块，曾得到更小的 280 blocks / 70 shards、
419,367 次块入口，以及约 304–318 / 116–140 ms 的稳态/无重建最好值；GPIOB service 也接近 0。
块内 VDD/ODR 缓存进一步把每轮 4 次采样压到 1 次。

但这组数据**不具备正确性**：宿主电气求解只在块边界运行，多个 WR 低→高脉冲被折叠成最终电平，
`MICA_JOINT=1` 的真实 MCU + ILI9325 测试失败，`R02h` 等初始化寄存器保持 0。最终版本因此：

- 在每个可能改变引脚的静态 GPIO 写之后收块；
- 仍在该块内直接生成 ODR 与 pin intent，不回到 GPIO service；
- 删除块内共享缓存（收块后每个有效边沿块最多只有一次翻转，已无共享对象，缓存实测反而
  多 1 个 shard、无重建最好值退化 163 → 175 ms）。

最终以 311 blocks / 71 shards、1,372,502 次入口换来每个 WR 边沿的完整电气可见性。

## 7. 测量注意

- 百分比是 profiler self samples，不是墙钟占比；
- profiler 会增加绝对耗时，读数用于相对归因；
- 稳态窗口使用 10 ms 宿主切片，包含每片 `program.run` 的固定进入成本；
- 动态块入口插桩只用于计数，不用于计时；
- 精确值随 Node/V8、宿主和代码版本变化，以 `bench/hal-throughput.test.ts` stdout 为准。
