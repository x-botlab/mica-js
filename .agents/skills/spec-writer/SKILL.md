# 工程技术规范写作 Skill

## 目标与适用范围

将需求、设计草案和现有实现整理为**精确、精简、可实现、可评审、可测试**的中文技术规范。借鉴 RFC 的术语一致性、明确约束、边界覆盖和可验证性；章节按具体项目组织。

## 语言与规范性表达

- 正文、标题、表格、审查意见和测试清单默认使用简体中文；代码、API 路径、字段名及固有技术标识符保持原样。
- 规范性关键词使用 **MUST / MUST NOT / SHOULD / SHOULD NOT / MAY**；在首次采用时说明约束强度。只为实际需要的规范性要求使用大写关键词。
- 每项要求尽量包含：**主体、适用条件、行为、可观察结果**。明确术语、单位、范围、状态与时序。
- 先呈现系统的能力与行为，再介绍必要的约束与例外；采用自然、准确的工程语言。

## 关键写作规则：正向定义优先

LLM 容易为了显得谨慎而反复写“没有 X”“不支持 X”“不依赖 X”“不保证 X”“本文不涉及 X”。这种写法往往占据篇幅，却没有增加可以实现或验证的信息。

**默认做法：描述实际存在的机制、承诺的行为以及明确的边界。** 对缺席的技术、功能和流程保持沉默，除非其缺席本身构成重要的接口契约、设计限制或风险信息。

### 何时写否定约束

符合以下至少一项时，保留必要的否定陈述：

1. **防止错误实现**：例如“已经撤销的凭据 MUST NOT 用于授权”。
2. **明确会影响调用方的契约边界**：例如客户端需要知道服务端是否自动重试、是否提供事务保证。
3. **解释非显然的设计权衡或风险**：例如跨外部系统的副作用无法由当前组件单独保证恰好一次。
4. **澄清真实且容易发生的范围误解**：只在范围章节集中解释一次。

其余情况优先省略，尤其避免逐项罗列“没有使用的技术”“未实现的特性”“无关的兼容对象”和“不适用的章节”。

### 具体改写策略

- **先写肯定的可观察行为**：优先“失败时返回 `409`，调用方通过新版本号重试”，而非连续写“不会覆盖、不自动合并、不保证更新成功”。
- **把限制放到对应行为附近**：与授权相关的 MUST NOT 放在授权章节；与重试有关的限制放在重试语义中。不要在摘要、目标、实现、测试中反复声明同一件事。
- **范围主要用正向列表定义**：先明确覆盖的功能；只有对读者判断方案有影响的排除项才列入“范围边界”。
- **用具体机制代替防御性措辞**：与其写“系统不保证绝对可靠”，不如说明“处理节点失败后，由租约过期触发重新分配；任务可能重复执行”。
- **保留必要的硬性禁止**：对安全性、不变量、互操作性有约束意义的 MUST NOT 不需要改写成肯定句。准确性始终高于文风偏好。
- **避免自我评价和模板声明**：正文不写“本文不讨论无关内容”“本方案并非万能解决方案”之类与实现无关的话。

完整的前后对照参见 `references/positive-writing-examples.md`。

## 设计信息的可信度

区分：**已确认（Confirmed）**、**推断（Inferred）**、**建议（Proposed）**、**待决（Open）**。重要的推断注明依据，设计建议不能悄然升级为已确定的 MUST 要求。

明确来源后再写具体超时、阈值、错误码、一致性等级、默认值、算法选择；缺少依据时以建议或待决项表达。保持对设计能力和风险的准确描述。

## 工作流程

### 1. 提取需求与系统边界

提取目标、读者、系统角色、已知约束、外部依赖、关键接口和既有设计决策。提问仅用于解决阻断性缺口；其余可记录假设后推进。

### 2. 先建立模型，再组织文字

根据场景建立术语、实体与字段、状态转换、不变量、事件与交互顺序。简单场景使用轻量模型，复杂状态系统使用状态表或时序图。

### 3. 确定可观察的行为契约

逐项界定前置条件、成功结果、错误结果、并发语义、版本语义、重试语义、边界行为。把“可靠”“快速”“安全”等抽象目标转换为可验证条件，或标记为待决指标。

### 4. 按需检查异常与边界

关注非法输入、重复操作、乱序、竞争、部分失败、超时、取消、重启、资源耗尽、安全边界和兼容性。将**确实影响实现或调用方**的结论写入规范；内部检查中不相关的项无需逐一呈现在成稿中。

### 5. 生成文档

按需参考 `references/template.md`，围绕当前项目选择章节。对可追踪要求使用 `REQ-001` 等编号；使用表格表达状态转换、字段约束和错误码。给出必要示例，但不以无关内容填充篇幅。

### 6. 双重审查

**技术审查**：检查术语歧义、矛盾、缺失条件、不可测试条款、边界行为与无依据的默认值。

**表达审查（特别重要）**：检索“没有 / 不支持 / 不保证 / 不提供 / 不依赖 / 不涉及 / 无须 / 不适用”等否定句：

- 如果删掉不影响实现、调用、测试或风险判断：**删除**。
- 如果改成行为定义更清晰：**改写成正向、可观察的描述**。
- 如果属于安全禁止或重要契约边界：**保留一次，放在最相关的章节**。
- 如果同一否定性声明跨章节重复：**合并，必要处交叉引用**。
- 避免“为了严谨”而额外添加没有事实支撑的免责式声明。

### 7. 交付

默认交付完整中文规范、必要的待决问题，以及与关键要求对应的精简验收检查清单。用户只要求小范围编辑时，只交付受影响内容。文档优先呈现**已定义的能力及行为**，让未定义或未采用的内容退居次要位置。

## 交付前检查

- 读者能否独立实现和验证关键功能？
- 术语、状态与行为约束是否一致？
- 每条 MUST / MUST NOT 是否有必要、适用条件和检验方法？
- 重大异常、故障、并发和安全条件是否得到准确描述？
- 建议、推断、已确认事实与待决事项是否区分清楚？
- 正文是否由**实际行为和工程决策**主导，而非反复强调“没有什么”？
- 每一条否定性声明是否对实现、接口契约、验证或风险判断有实际价值？
- 章节和示例是否与项目有关，语言是否简洁自然？
